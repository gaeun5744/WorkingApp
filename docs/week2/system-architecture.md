# 만보기 시스템 아키텍처 (2주차 과제)

> 질문: **"만보기 앱에 서버와 DB가 왜 필요하고, 데이터가 어떻게 이동하는가?"**
> 답 한 줄: 걸음은 **기기가 세고 보관**하지만(오프라인에서도 보여야 하므로), 돈이 걸린 판정(리워드)과 사람 사이 비교(랭킹)는 **기기가 조작할 수 없는 서버가 자기 DB 값으로** 한다. 그 사이를 15분 주기의 멱등 배치 업로드가 잇는다.
>
> 기준 코드: Phase A(앱 + Mock 서버) 완성본. 서버(Phase B)는 설계안이며 `docs/week1/TODO.md` M8~M12에서 구현한다.
> 관련 문서: API 계약 `docs/week2/api.md`, 코드 구조 `docs/week2/architecture.md`, 결정 근거 `docs/week1/PRD.md`, 확인 기록 `docs/week2/scenarios.md`

│  StepSnapshotWorker (WorkManager 15분, 서비스가 죽었을 때 대비)       │        │   ├ 인증: 익명 가입, JWT 발급·검증, 리프레시 토큰 교체           │

│      │  한 트랜잭션: 증분 + 체크포인트                                 │        │   ├ 보물상자: 위치 검증 → 지급                                  │

│  Room (기기의 걸음 원천)                                             │        │      │                                                       │
│   daily_steps(synced) · hourly_steps · counter_checkpoint            │        │      ▼                                                       │
│      │ Flow                          │ synced=0 인 날짜               │        │  PostgreSQL (서버의 원천: 사용자·걸음·리워드·지갑)              │
│      ▼                               ▼                               │        │  [Redis: 필요성 측정 후 랭킹용으로 추가 — W2-Q1]                │
│  ViewModel → Compose UI         StepSyncWorker (15분, 네트워크 조건)   │        │                                                              │
│  (화면은 서버를 기다리지 않음)    + 지수 백오프                         │        │  Play Integrity API (Google) ◀── 리워드 수령 시 토큰 검증      │
│                                      │                               │        │                                                              │
│                                      ▼                               │        └──────────────────────────────────────────────────────────────┘
│                    Retrofit → OkHttp ─ AuthInterceptor(토큰 첨부·401 갱신) ──── HTTPS ────▶

데이터 원천은 둘로 나뉜다 (PRD Q5).

| 데이터 | 원천 | 이유 |
|---|---|---|
| 걸음 측정값 (화면 표시) | **기기 Room** | 오프라인에서도 숫자가 바로 올라가야 한다. 서버를 기다리면 지하철에서 화면이 멈춘다 |
| 리워드 판정, 지갑 잔액, 랭킹 | **서버 PostgreSQL** | 기기 값은 조작할 수 있다. 돈(포인트)과 다른 사람과의 비교는 서버가 받은 값으로만 한다 |

## 2. 구성 요소별 역할

### Android

| 구성 요소 | 역할 | 왜 필요한가 / 없으면 어떤 문제가 생기나 |
|---|---|---|
| STEP_COUNTER 센서 | 부팅 후 누적 걸음 제공 | 걸음 감지를 칩이 저전력으로 한다. 가속도계로 직접 세면 배터리가 크게 든다 |
| `StepCounterService` (FGS, type=health) | 앱이 꺼져도 센서를 구독 | 없으면 앱을 닫는 순간 측정이 멈춘다. 상시 알림이 필요한 대가 |
| `StepSnapshotWorker` (15분) | 서비스가 죽었을 때 한 번씩 센서를 읽음 | 제조사 절전 정책으로 서비스가 죽어도 측정 공백을 15분 수준으로 줄인다 |
| `BootCompletedReceiver` | 재부팅·앱 업데이트 후 서비스 재시작 | 없으면 재부팅 후 사용자가 앱을 열 때까지 측정이 안 된다 |
| `StepDeltaCalculator` (순수 Kotlin) | 누적값 → "언제 몇 걸음" 변환. 재부팅·늦게 온 측정·측정 공백 처리 | 핵심 규칙을 Android 없이 단위 테스트한다. 틀리면 걸음이 중복되거나 한 시간에 몰린다(§6 실제 사례) |
| Room | 날짜별·시간대별 걸음, 체크포인트, `synced` 플래그 | 프로세스가 죽어도 남아야 한다. 증분과 체크포인트를 한 트랜잭션으로 저장해야 중복·누락이 없다 |
| ViewModel + Compose | Room Flow를 화면 상태로 | 화면은 로컬 데이터만 본다. 네트워크 상태와 무관하게 즉시 갱신 |
| `StepSyncWorker` (WorkManager) | 미동기화 날짜 배치 업로드 | 앱이 꺼져 있어도, 네트워크가 돌아오면 OS가 실행해 준다. 직접 스레드로 하면 앱이 죽을 때 같이 죽는다 |
| `AuthInterceptor` + `AccessTokenRenewer` | 토큰 첨부, 401이면 갱신 후 재시도, 갱신도 실패하면 조용히 재가입 | 화면 코드마다 토큰 처리를 넣지 않는다 |
| `MockApiInterceptor` (Phase A) | `docs/week2/api.md` 규칙을 앱 안에서 흉내 | 서버 없이 앱을 끝까지 만들고, 계약을 먼저 검증한다. 실제 네트워크 실패는 재현하지 못한다 |

### 서버 (Phase B 설계)

| 구성 요소 | 역할 | 왜 필요한가 / 없으면 어떤 문제가 생기나 |
|---|---|---|
| Caddy | HTTPS 종료, 인증서 자동 갱신 | 없으면 토큰과 걸음이 평문으로 오간다. 인증서 갱신을 사람이 챙겨야 한다 |
| API Server (Spring Boot) | 인증·검증·판정·지급 | 기기를 믿지 않는 유일한 판정자. 상태는 DB에 두고 서버는 무상태(JWT)라 여러 대로 늘릴 수 있다 |
| 걸음 처리 | 날짜·미래 시간대·상한 검사 → `max(기존, 새 값)` upsert | 같은 요청을 여러 번 받아도 결과가 같다(멱등). 재시도가 안전해진다 |
| 리워드 처리 | 서버 걸음으로 구간 판정 → `UNIQUE(user, date, tier)` + 잔액 갱신을 한 트랜잭션으로 | 앱이 "1만 보 걸었어요"라고 해도 믿지 않는다. 동시 요청에도 1회만 지급 |
| PostgreSQL | 사용자·걸음·리워드·지갑의 원천 | 서버가 재시작돼도 디스크에 남는다. 트랜잭션·유니크 제약으로 돈 관련 정합성을 DB가 보장 |
| Redis (보류) | 랭킹 정렬 캐시 | 지금 규모에서는 PostgreSQL 인덱스로 충분할 수 있다. M10에서 측정 후 결정 (W2-Q1) |
| Play Integrity | 변조 앱·루팅 기기 판별 | 규칙 검사만으로는 "정상처럼 보이는 조작 앱"을 구분할 수 없다 |

## 3. 핵심 개념 5가지 — 이 프로젝트의 답

| 개념 | 질문 | 답 |
|---|---|---|
| Client-Server | 걸음 수를 왜 서버에 저장하나? | ① 리워드·랭킹을 기기가 조작할 수 없게 하려고 ② 재설치·기기 변경 시 복원(`GET /steps`) ③ 다른 사용자와 비교하려면 한곳에 모여야 한다. 대신 **화면 표시는 서버에 의존하지 않는다** |
| REST API | 걸음 수를 어떤 API로 보내나? | `POST /steps/sync` — 걸음마다가 아니라 **날짜별 누적값 배치**. 누적값을 보내므로 서버는 `max`만 하면 되고, 중복 전송·순서 뒤바뀜에 안전하다. 증분(+100)을 보냈다면 재시도 때마다 걸음이 늘어난다 |
| API Server | 1만 보 달성 여부는 어디서 판단하나? | **서버**. 서버가 받아 둔 `daily_steps`로만 판정한다. 앱의 "받기 가능" 표시는 버튼을 켜는 UX일 뿐이고, 수령 직전에 동기화해서 서버 값을 최신으로 만든다 |
| Database | 서버가 재시작되면 데이터는? | PostgreSQL이 원천이라 그대로다. 메모리에만 있는 것은 없게 한다. Redis를 쓰게 되면 DB에서 다시 만들 수 있는 파생 데이터로만 쓴다 |
| 확장성 | 서버 한 대가 부족하면? | 먼저 숫자: MAU 10만·DAU 3만이면 평균 약 33 RPS, 피크 100~170 RPS로 1대로 충분하다(`PLAN.md` 계산). 부족해지면 ① 서버를 무상태로 유지했으니 로드 밸런서 뒤에 여러 대 ② DB 읽기 복제본(랭킹·조회) ③ 캐시(Redis) 순서. 쓰기 병목은 동기화 주기·배치 크기 조정이 가장 싸다 |

## 4. 걸음 저장·조회 API (상세: `docs/week2/api.md`)

### `POST /steps/sync` — 저장

```json
{ "days": [ { "date": "2026-11-03", "steps": 5230, "hourly": [ { "hour": 8, "steps": 2100 }, { "hour": 9, "steps": 3130 } ] } ] }
→ { "results": [ { "date": "2026-11-03", "status": "ACCEPTED", "acceptedSteps": 5230 } ] }
```
- 최근 7일만 받음, 미래 날짜·미래 시간대 거부
- 상한(시간당 12,000 / 하루 100,000) 초과는 잘라서 `CAPPED` + 의심 표시
- `저장값 = max(기존, acceptedSteps)` → 멱등

### `GET /steps?from=&to=` — 조회 (2주차 추가)

```json
→ { "days": [ { "date": "2026-11-02", "steps": 8120 }, { "date": "2026-11-03", "steps": 6783 } ] }
```
- 서버가 **인정한** 값(상한 적용 후)을 준다. 기기 값보다 작을 수 있다
- 기록 있는 날만, 최대 31일, 일별만
- 용도: 재설치·기기 변경 복원(3주차에 병합 규칙 설계), 서버 판정값 확인

## 5. 데이터 흐름 시나리오

### A. 사용자가 100걸음을 걸었다 (정상)

```
센서 이벤트(걸음마다) → StepCounterService → StepRepository.record()
  → [트랜잭션] 체크포인트 읽기 → StepDeltaCalculator(+1) → daily/hourly += 1, synced=0, 체크포인트 갱신
  → Room Flow → HomeViewModel → 화면 숫자 +1
(서버 호출 없음)
… 최대 15분 뒤 StepSyncWorker → POST /steps/sync (그날 누적값) → 200 → synced=1
```
- **매번 서버를 부르지 않는 이유**: 화면 표시용(즉시, 로컬)과 서버 저장용(판정·비교, 늦어도 됨) 데이터의 요구가 다르다. 걸음마다 요청하면 하루 수천 건 × 사용자 수, 배터리·데이터 낭비. WorkManager 주기 작업은 최소 15분이고 실행 시각도 보장되지 않는다(가이드 [1])
- 서버 값이 늦어서 문제가 되는 곳은 리워드뿐이라, 그때만 수령 직전 동기화로 보완한다(시나리오 C)

### B. 인터넷이 끊겼다가 복구됐다 (오프라인) — 에뮬레이터 확인함

```
오프라인: 걸음은 계속 Room 에 쌓임 (synced=0) → StepSyncWorker 는 CONNECTED 제약으로 실행 대기
복구:     OS 가 제약 충족을 감지 → 약 1.5초 뒤 작업 실행 → POST /steps/sync
          토큰이 만료됐으면 401 → /auth/refresh → 재시도 → 200
업로드 중 새 걸음이 기록되면 그 날짜는 synced=0 으로 남아 다음에 다시 보냄
요청 실패(네트워크·5xx) → Result.retry() → 지수 백오프(30초부터)
```
- **중복 전송**이 안전한 이유: 날짜별 누적값 + 서버 `max`. 같은 날짜를 열 번 보내도, 순서가 바뀌어도 결과가 같다
- **실패 처리**: 서버가 응답을 줬다면(ACCEPTED·CAPPED·REJECTED) 다시 보내지 않는다. 응답을 못 받았을 때만 재시도
- 근거: `docs/week2/scenarios.md`

### C. 사용자가 1만 보를 달성했다 (리워드)

```
[받기] 탭 → HomeViewModel
  ① 응답 대기 중이거나 이미 받은 구간이면 무시 (연타 방지)
  ② 낙관적 표시 "받음"
  ③ StepRepository.syncPendingSteps()  — 서버 걸음을 최신으로 (실패 → 되돌림)
  ④ POST /rewards/claim { date: 오늘, tier, integrityToken }
서버 (한 트랜잭션)
  ⑤ Play Integrity 검증 → 오늘(KST)인지 → 서버 daily_steps ≥ 구간 걸음인지
  ⑥ INSERT reward_claims (UNIQUE user, date, tier) → 지갑 잔액 + 내역
     이미 있으면 → 기존 결과 반환 (alreadyClaimed: true), 포인트 추가 없음
  ⑦ 응답 → 앱 확정 또는 되돌림 + 코드별 안내
```
- **최종 결정은 서버**: 앱 판정은 버튼 표시용. 앱이 결정하면 조작된 앱이 포인트를 찍어낸다
- **중복 지급 방지는 DB 유니크 제약**: 앱의 연타 방지는 UX일 뿐이다. 동시에 두 요청이 와도 하나만 INSERT에 성공한다 (4주차에 깊게)

## 6. 내 설계의 약점 2가지

### 약점 1. 기기가 측정을 못 하는 동안의 걸음은 "언제" 걸었는지 알 수 없다 — **실기기에서 실제로 발생**

- 사례(2026-11-03, SM-S916N): 앱이 강제 중지된 채 일주일이 지나고 그 사이 재부팅까지 겹쳤다. 앱을 연 순간 센서 누적값 19,544보(재부팅 후 2.5일치)가 **오늘 20시 한 칸**에 들어갔다
- 파급: 오늘 걸음 부풀림 → 리워드 구간이 풀릴 수 있음, 시간당 상한 초과로 서버 값과 기기 값이 달라짐, 재부팅 전 걸음은 영구 손실
- 원인 구조: 강제 중지된 앱은 OS가 아무것도 실행해 주지 않는다(서비스·워커·부팅 수신기 모두). 클라이언트 측정에 공백이 생기면 그 공백은 결국 **서버에 잘못된 데이터**로 도착한다
- 보완(적용함): 1시간 넘는 공백은 공백 구간에 시간 비율로 나눈다(`StepDeltaCalculator`). 날짜별 합계는 대략 맞지만 시간대별 값은 추정치다
- 남은 대안: Health Connect·Recording API처럼 OS가 대신 기록해 둔 데이터로 공백을 채우기 (3주차 동기화 알고리즘에서 검토)

### 약점 2. 걸음 수는 결국 클라이언트가 보낸 값을 믿는다

- 서버가 할 수 있는 건 "그럴듯한지" 검사뿐이다: 시간당·하루 상한, 미래 시간대 거부, Play Integrity(변조 앱·루팅)
- 정상 앱 + 정상 기기에서 **폰을 흔들거나 기계에 올려 두는** 조작은 막지 못한다. 상한 이하로만 흔들면 통과한다
- 보완 방향: 시간대별 패턴 이상 탐지(새벽 3시 1만 보), 보물상자처럼 위치가 필요한 보상 비중 늘리기, 포인트에 지급 한도. 완전한 해결은 없고 **비용 대비 어디까지 막을지의 정책 문제**다

### 그 밖에 알고 있는 약점

- 동기화 최대 15분 지연 → 랭킹이 늦게 반영된다 (리워드는 수령 직전 동기화로 보완)
- VM 1대 + DB 1대 → 단일 장애 지점. 장애 중에도 걸음 측정·표시는 기기에서 계속되고 복구 후 업로드되므로, 영향은 리워드·랭킹 지연으로 한정된다
- 재설치 시 기기 기록 손실 → `GET /steps`로 복원 가능하게 계약만 만들어 둠 (앱 적용은 3주차)

## 7. 기술 선택표 — 왜 썼나 / 없으면

| 기술 | 왜 썼나 | 없으면 생기는 문제 | 검토한 대안 → 선택 안 한 이유 |
|---|---|---|---|
| STEP_COUNTER | 센서·백그라운드·재부팅 처리를 직접 공부 (PRD Q8) | — | Health Connect: 구현은 쉽지만 측정 설계를 배울 수 없음. Recording API: Android 13 이하도 지원하지만 Play 서비스 의존 + 병합 규칙 필요 → 약점 1 보완책으로 3주차 재검토 |
| Foreground Service | 앱이 꺼져도 측정 | 앱을 닫으면 측정 중단 | 워커만 사용: 15분 간격이라 화면·알림이 실시간이 아니고, 공백 처리 오차가 커짐 |
| Room | 기기 원천 데이터, 트랜잭션 | 프로세스 종료 시 유실, 증분·체크포인트 불일치로 중복 | DataStore: 표 형태 데이터와 트랜잭션에 맞지 않음 |
| WorkManager | OS가 조건(네트워크)·재시도·재부팅 후 재예약을 관리 | 직접 스레드: 앱이 죽으면 같이 죽고, 오프라인 대기·백오프를 직접 구현 | AlarmManager: 정확한 시각이 필요 없고 제약 조건이 없음 |
| Retrofit + OkHttp | 계약(`api.md`)을 인터페이스로, 인증·Mock을 Interceptor로 | 화면마다 HTTP·토큰 코드 중복 | — |
| JWT (액세스 1시간 / 리프레시 30일, 교체) | 서버 무상태 → 수평 확장 가능 | 세션을 서버 메모리에 두면 서버를 늘릴 때 세션 공유 필요 | 서버 세션: 확장 시 Redis 등 공유 저장소 필요 |
| PostgreSQL | 트랜잭션, 유니크 제약, `ON CONFLICT` upsert | 중복 지급·잔액 불일치를 애플리케이션 코드로 막아야 함 | MySQL: 같은 기능(`ON DUPLICATE KEY UPDATE`, `GREATEST`)이 있어 결정적 차이는 없다. 1주차 스택 결정을 따름 (2주차에 대안으로 추가 기록) |
| Caddy | HTTPS 자동화 | 평문 통신, 인증서 수동 갱신 | Nginx + certbot: 설정·갱신 작업이 더 많음 |
| Play Integrity | 변조 앱·루팅 판별 | 조작 앱이 규칙 검사를 통과 | 규칙 검사만: 정상처럼 보이는 조작 구분 불가 (PRD Q9) |
| Redis | (보류) 랭킹 정렬 | 지금은 없음 — DB 인덱스로 시작 | 처음부터 도입: 근거 없는 구성 요소 추가 (W2-Q1) |
