# 만보기 앱 클론 — PRD

> 당근 만보기를 참고해 앱 시스템 디자인을 연습하는 프로젝트의 요구사항 문서.
> 상태: **M0 확정** (2026-10-25)

## 1. 목표

센서에서 시작한 걸음 데이터가 기기 저장소 → 서버 → 리워드·랭킹까지 **정확하고, 오프라인에서도 유실 없이, 조작에 강하게** 흐르는 시스템을 Android 앱과 Spring Boot 서버로 직접 설계·구현한다.

## 2. 범위

### 하는 것 (In scope)
- 오늘 걸음 수 실시간 표시, 일일 목표 설정·달성률
- 일/주/월 걸음 기록 그래프
- 구간별 리워드 포인트 수령, 지갑 잔액·적립 내역
- 동네(목록 선택) 일간·주간 랭킹
- 익명 가입 + JWT 토큰 인증
- 백그라운드 측정(Foreground Service), 재부팅·자정·시간 변경 처리
- 오프라인 우선 동기화, 서버 측 어뷰징 검증 + Play Integrity
- 실제 백엔드(Spring Boot) 구현 및 클라우드 배포

### 하지 않는 것 (Non-goals)
- Health Connect 연동, 워치 데이터
- 알림(리워드·목표·랭킹). 단, Foreground Service 상시 알림은 OS 요구사항이라 유지
- 앱 삭제·기기 변경 시 계정 복구, 이메일/소셜 로그인
- 포인트 사용·현금 전환
- GPS 동네 인증, 거짓 동네 선택 방지
- 흔들기 패턴(가속도) 분석
- 관리형 DB/Redis, 오토스케일링

## 3. 시스템 개요

```
[Android]                                         [Server: VM + Docker Compose]
 STEP_COUNTER → StepCounterService → Room ──SyncWorker──▶ Caddy(HTTPS) → Spring Boot
                                      │                                    │      │
                                  ViewModel → Compose UI          PostgreSQL(원천)  Redis(랭킹 ZSET)
```

- 걸음 측정의 원천: **기기(Room)** / 리워드·랭킹의 원천: **서버(PostgreSQL)**
- 날짜 기준: **Asia/Seoul 고정**, 서버 시계로 "오늘" 판정

## 4. 수용 기준 (Acceptance Criteria)

- [ ] 앱 강제 종료·재부팅 후에도 그날 걸음 수가 유지된다.
- [ ] 자정(KST)이 지나면 전날 기록이 확정되고 오늘 걸음이 0부터 시작한다.
- [ ] 비행기 모드로 걷고 다시 연결하면 서버 값이 기기 값과 같아진다.
- [ ] 같은 업로드 요청을 여러 번 보내도 서버 값이 바뀌지 않는다(멱등).
- [ ] 같은 구간 리워드를 동시에·반복해서 요청해도 포인트는 한 번만 적립된다.
- [ ] 하루/시간당 상한을 넘는 업로드는 상한으로 잘리고 의심 플래그가 남는다.
- [ ] Play Integrity 검증 실패 시 리워드가 지급되지 않는다(로컬 개발 설정에서는 검증 생략 가능).
- [ ] 동네 일간·주간 랭킹에서 상위 N명과 내 순위를 볼 수 있다.
- [ ] Redis 데이터를 지워도 PostgreSQL에서 랭킹을 재구축할 수 있다.
- [ ] 배포된 HTTPS 서버에 실제 기기로 접속해 위 시나리오가 동작한다.

## 5. 엣지 케이스

| 상황 | 처리 |
|---|---|
| 재부팅으로 센서 누적값 리셋 | `BOOT_COUNT` 변화(알 수 없으면 값 감소)로 재부팅 판정 → 현재 값 전체를 증분으로 반영 (`docs/architecture.md` §3) |
| 자정 경계 | 증분을 측정 시각(KST)의 날짜에 더하므로 별도 리셋 없음 |
| 기기 시간·시간대 조작 | 앱은 KST로 계산, 서버는 자기 시계로 날짜 판정 · 미래 날짜/시간대 거부 |
| 장기간 오프라인 | 미동기화 행 보관, 허용 기간 내 업로드 |
| 권한 거부 (`ACTIVITY_RECOGNITION`) | 측정 불가 안내 + 설정 이동 UI |
| 센서 미지원 기기 | 미지원 안내 UI |
| 토큰 만료 | 리프레시 토큰으로 재발급, 실패 시 재가입 흐름 |
| 리워드 요청 중 네트워크 끊김 | 재시도해도 멱등 키로 중복 지급 없음 |

## 6. 세부 수치 (Q16에서 확정, 구현하며 조정 가능한 설정값)

| 항목 | 기본값 |
|---|---|
| 리워드 구간 / 포인트 | 1천/3천/5천/7천/1만 보 → 1/3/5/7/10P |
| 하루 걸음 상한 | 100,000보 |
| 시간당 걸음 상한 | 12,000보 |
| 늦은 업로드 허용 기간 | 최근 7일 (오늘 포함) |
| 백그라운드 동기화 주기 | 15분 (WorkManager 최소 주기) + 앱 진입 시 |
| 랭킹 노출 | 상위 50명 + 내 순위 |
| 앱 랭킹 캐시 | 5분 |
| 액세스 / 리프레시 토큰 만료 | 1시간 / 30일 |

## 7. 의존성 / 제약

- Play Integrity: Play Console 앱 등록 + 내부 테스트 트랙 배포, Google Cloud 프로젝트
- 클라우드 VM 1대 + 도메인(HTTPS 인증서 발급용)
- GitHub 저장소(Actions 배포용)
- `.agents/` 지침은 Android 전용 → 서버용 규칙 문서 별도 필요

## PRD Interview

각 결정마다 **검토했지만 선택하지 않은 대안과 이유**를 함께 기록한다.

### Q1. 서버(백엔드)를 어디까지 만들까? → **실제 백엔드도 구현**
- 선택 이유: 리워드 검증·동기화·랭킹을 실제 서버에서 다뤄 보며 클라이언트-서버 전체 설계를 연습한다.
- 선택하지 않은 대안
  - 앱 + 가짜 서버(Interceptor/MockWebServer): 앱 설계에는 집중할 수 있지만 서버 측 동시성·트랜잭션·검증을 실제로 겪어 볼 수 없다.
  - 서버 없이 로컬만: 가장 단순하지만 동기화·어뷰징 방지 설계를 공부할 수 없다.

### Q2. 백엔드 기술 스택은? → **Spring Boot (Kotlin)**
- 선택 이유: 실무에서 가장 흔한 스택이고, 언어는 앱과 같은 Kotlin.
- 선택하지 않은 대안
  - Ktor: 가볍고 앱과 라이브러리(kotlinx.serialization, Coroutines)를 공유하지만 실무 보급도가 낮다.
  - Firebase/Supabase: 빠르지만 멱등성·검증 같은 서버 로직을 직접 설계할 기회가 줄어든다.

### Q3. 서버 코드는 어느 저장소에? → **같은 저장소, 빌드 분리**
- 선택 이유: `server/`를 앱과 독립된 Gradle 프로젝트로 두어 API 변경을 한 브랜치에서 함께 다루고, AGP와 Spring 플러그인 충돌을 피한다. `docs/api.md`가 계약의 기준.
- 선택하지 않은 대안
  - 같은 저장소 + DTO 공유 모듈: 타입 불일치는 없지만 빌드가 복잡해지고 단일 모듈 원칙과 어긋난다.
  - 별도 저장소: 실무와 비슷하지만 혼자 API를 바꿀 때마다 두 저장소를 오가야 한다.

### Q4. 사용자 식별 방식은? → **익명 가입 + 토큰**
- 선택 이유: 첫 실행 시 서버가 사용자를 만들고 액세스/리프레시 토큰(JWT)을 발급한다. 토큰 갱신·인증 실패 처리 설계는 그대로 배우면서 로그인 UI 부담이 없다.
- 선택하지 않은 대안
  - 이메일/비밀번호: 기기를 바꿔도 계정이 유지되지만 만보기 핵심과 무관한 작업이 늘어난다.
  - 소셜 로그인: 실제 앱과 가장 비슷하지만 콘솔 설정과 서버 측 ID 토큰 검증 준비가 많다.

### Q5. 걸음 수의 진실의 원천은? → **역할 분리**
- 선택 이유: 걸음 측정은 기기(Room)가 기준, 리워드·랭킹은 서버가 기준. 기기는 날짜별 누적 걸음을 올리고 서버는 `max(기존, 새 값)`으로 반영해 재시도가 안전하다(멱등). 리워드는 서버가 받은 값으로만 판정.
- 선택하지 않은 대안
  - 서버가 모두 기준: 값은 항상 일치하지만 오프라인일 때 화면 숫자가 멈춰 오프라인 우선 요구와 충돌한다.
  - 기기가 모두 기준: 구현은 쉽지만 값 조작을 막을 수 없다.

### Q6. ‘오늘’의 날짜 기준은? → **한국 시간(Asia/Seoul) 고정**
- 선택 이유: 국내 서비스이고 동네 랭킹이 같은 날짜 기준이어야 공정하다. 서버는 자기 시계로 오늘을 판정하고 미래 날짜·허용 기간 밖 업로드는 거부. 리워드는 오늘 것만 수령.
- 선택하지 않은 대안
  - 기기 현지 시간대: 해외에서 자연스럽지만 시간대 정보 검증과 "하루 두 번 만들기" 어뷰징 방어가 추가로 필요하다.

### Q7. 리워드 규칙은? → **구간별 고정 포인트**
- 선택 이유: 하루 5구간, 버튼을 눌러 고정 포인트를 지갑에 적립. 잔액·내역을 서버가 관리해 멱등성·트랜잭션을 공부하기 좋다. 원본 앱과 다르면 보정.
- 선택하지 않은 대안
  - 구간별 랜덤 포인트: 재시도 시 같은 결과를 돌려주도록 결과 저장이 필요해 멱등성 설계가 한 단계 복잡해진다.
  - 목표 달성 시 1회만: 가장 단순하지만 구간별 상태(잠김/수령 가능/수령 완료) 연습이 줄어든다.

### Q8. 걸음 데이터 소스는? → **STEP_COUNTER 단독**
- 선택 이유: 센서·Foreground Service·재부팅/자정 처리를 직접 구현하는 것이 핵심 학습. `StepDataSource` 인터페이스로 분리해 Fake로 교체 가능.
- 선택하지 않은 대안
  - Health Connect 단독: 구현은 쉬워지지만 센서·백그라운드 설계를 공부할 수 없고 기기 의존성이 생긴다.
  - 둘 다: 워치 데이터까지 담을 수 있지만 두 소스 간 중복 제거 규칙이 필요해 M1 범위가 커진다.

### Q9. 서버 어뷰징 검증 범위는? → **규칙 기반 검사 + Play Integrity**
- 선택 이유: 앱이 시간대별(hourly) 걸음을 함께 업로드하고, 서버는 ① 하루 상한 ② 시간당 상한 ③ 미래 시간대 거부를 검사한다. 상한 초과분은 잘라내고 의심 플래그를 남긴다. 리워드 수령 시 Play Integrity 토큰을 서버에서 검증해 변조 앱·루팅 기기를 막는다.
- 선택하지 않은 대안
  - 규칙 기반 검사만: 설정이 간단하지만 변조된 앱을 구분할 수 없다.
  - 하루 상한만: 가장 단순하지만 상한 이하의 흔들기 어뷰징을 전혀 막지 못한다.

### Q10. 동네 결정 방식은? → **목록에서 선택**
- 선택 이유: 서버에 동네 목록을 시드 데이터로 두고 검색·선택. 위치 권한이 필요 없고, 동네 선택 결과 전달로 `ResultEventBus`를 연습한다.
- 선택하지 않은 대안
  - GPS 동네 인증: 실제 앱과 가장 비슷하지만 위치 권한, 좌표→행정동 변환(역지오코딩), 인증 만료 정책이 추가된다.

### Q11. 랭킹 기간과 집계 방식은? → **일간 + 주간, Redis Sorted Set**
- 선택 이유: 대규모 랭킹 설계를 직접 해 본다. 일간은 `ZADD GT`로 더 큰 값만 반영하고, 주간(월요일 시작, KST)은 DB에서 실제로 증가한 만큼만 `ZINCRBY`. 원천은 PostgreSQL이고 Redis는 재구축 가능한 파생 데이터. 키에 TTL을 둔다.
- 선택하지 않은 대안
  - 일간만, DB 집계: 인프라가 가장 단순하지만 Redis 랭킹 설계를 경험할 수 없다.
  - 일간 + 주간, DB 집계: 주간은 7일 합계를 구해야 해서 쿼리가 무거워지고 배치 사전 집계까지 고민해야 한다.

### Q12. 서버 실행 환경은? → **클라우드 배포** (+ 개발용 로컬 Docker Compose)
- 선택 이유: 어디서나 실제 기기로 접속 가능한 HTTPS 서버, 배포 파이프라인까지 경험.
- 선택하지 않은 대안
  - 로컬 Docker Compose만: 비용이 없지만 같은 와이파이에서만 접속 가능하고 배포 경험이 빠진다.

### Q13. 클라우드 배포 형태는? → **VM 1대 + Docker Compose**
- 선택 이유: 로컬과 같은 Compose 구성을 VM(EC2/Lightsail/GCE 중 택1)에 올리고 Caddy로 HTTPS 자동 발급, GitHub Actions로 빌드·배포. 비용이 낮고 로컬과 환경이 같다.
- 선택하지 않은 대안
  - 관리형 서비스 조합(Cloud Run/ECS + RDS + ElastiCache): 실무에 가깝지만 비용이 크고 VPC 설정이 복잡하다.
  - PaaS(Railway/Render/Fly.io): 가장 빠르지만 인프라가 가려져 배우는 것이 적고 무료 한도가 자주 바뀐다.

### Q14. 알림 방식은? → **알림 기능 없음**
- 선택 이유: 사용자 결정. 리워드·목표·랭킹 알림 모두 비범위. Foreground Service 상시 알림만 OS 요구사항으로 유지.
- 선택하지 않은 대안
  - 로컬 알림만: 오프라인에서도 동작하고 서버 작업이 없지만 이번 범위에서는 불필요.
  - 로컬 + FCM 푸시: 푸시 토큰 관리·발송 큐 설계를 배울 수 있지만 Firebase 설정이 추가된다.

### Q15. 서버의 DB 접근 기술은? → **Spring Data JPA + 네이티브 upsert + Flyway**
- 선택 이유: 실무에서 가장 흔한 조합. 일반 CRUD는 JPA로, 걸음 업로드처럼 동시성이 중요한 곳은 `INSERT ... ON CONFLICT DO UPDATE SET steps = GREATEST(...)` 네이티브 쿼리로 원자적으로 처리한다. 리워드 중복은 `(user_id, date, tier)` 유니크 제약으로 막고, 스키마는 Flyway 마이그레이션으로 관리한다.
- 선택하지 않은 대안
  - **jOOQ**: SQL을 타입 안전한 Kotlin DSL로 작성해 upsert·랭킹 같은 복잡한 쿼리 표현력이 뛰어나다. 하지만 DB 스키마에서 코드를 생성하는 빌드 설정이 필요하고, 학습 자료와 실무 사례가 JPA보다 적다.
  - **Exposed**: JetBrains의 Kotlin 네이티브 SQL 라이브러리로 문법이 Kotlin스럽고 가볍다. 하지만 Spring 트랜잭션(`@Transactional`)과 함께 쓸 때 연동에 주의가 필요하고, 실무 보급도가 낮다.
  - JPA의 트레이드오프(인지하고 선택): 엔티티 변경 감지·지연 로딩 같은 추상화 때문에 실제 실행되는 SQL이 가려질 수 있고, `GREATEST` upsert 같은 DB 고유 기능은 결국 네이티브 쿼리로 내려가야 한다. 이 지점을 직접 겪어 보는 것도 학습 목표에 포함한다.

### Q16. 세부 수치 기본값을 확정할까? → **§6 기본값대로 확정**
- 선택 이유: 모두 나중에 바꾸기 쉬운 설정값이라 기본값으로 시작하고 구현하며 조정한다.
- 선택하지 않은 대안
  - 지금 값을 하나씩 정밀하게 결정: 근거 데이터(실사용 패턴)가 없는 상태라 정밀하게 정해도 의미가 적다.

### Q17. 구현 순서는? → **앱을 Mock 서버로 먼저 완성 → 그다음 실제 서버**
- 선택 이유: 사용자 결정. 앱 설계(측정·저장·동기화·UI)에 먼저 집중하고, 앱이 완성된 뒤 서버로 넘어간다. 이때 `docs/api.md`가 앱과 Mock, 이후 실제 서버 사이의 계약 역할을 한다.
- 선택하지 않은 대안
  - 서버 먼저: 실제 API로 바로 붙일 수 있지만 앱 학습이 뒤로 밀린다.
  - 앱·서버 기능 단위로 번갈아: 기능마다 끝까지 동작하지만 두 스택을 계속 오가야 해서 집중이 흩어진다.

### Q18. Mock 서버 방식은? → **앱 내부 OkHttp Interceptor (`MockApiInterceptor`)**
- 선택 이유: Retrofit·DTO·`Authenticator`·오류 처리 코드가 처음부터 실제 코드로 동작한다. 서버 전환 시 `BuildConfig.USE_MOCK_API` 플래그와 base URL만 바꾼다. 메모리 상태로 멱등 upsert, 리워드 중복 방지, 가짜 이웃 랭킹, 401·지연·오류 주입을 흉내 낸다.
- 선택하지 않은 대안
  - Fake Repository(네트워크 계층 없이 교체): 가장 단순하지만 DTO·Retrofit·토큰 재발급 코드가 서버 단계까지 검증되지 않는다.
  - 앱 내 MockWebServer 실행: 실제 HTTP 소켓까지 거치지만 앱 안에서 서버를 띄우는 설정이 번거롭고 Interceptor 대비 얻는 것이 적다.
  - 로컬 PC의 별도 Mock 서버(json-server, WireMock 등): 실제 서버와 구조가 비슷하지만 실행할 프로세스가 하나 더 생기고, 실제 기기에서 접속하려면 네트워크 설정이 필요하다.
- 알려진 한계: Mock 상태는 메모리에만 있어 앱 프로세스가 재시작되면 초기화된다(지갑·랭킹). Play Integrity는 Play Console 배포가 필요해 서버 단계(Phase B)에서 앱·서버를 함께 연동한다.

### Q19. 리프레시 토큰이 무효일 때(계정 복구 불가) 처리는? → **저장된 닉네임·동네로 조용히 자동 재가입**
- 선택 이유: 사용자 결정. 화면 흐름이 끊기지 않는다. Phase A의 Mock은 프로세스 재시작마다 상태가 사라지므로 이 흐름이 자주 일어난다.
- 함께 정해지는 것
  - 닉네임·동네를 기기에 저장한다 (재가입 입력값).
  - 재가입하면 로컬 걸음을 모두 "미동기화"로 되돌려 최근 7일치를 새 계정으로 다시 업로드한다. 그러지 않으면 새 계정의 서버 걸음이 0이 되어 리워드·랭킹이 틀어진다.
  - 알려진 트레이드오프: 이전 계정의 지갑 포인트는 사용자 모르게 사라진다 (Q4 비범위 "계정 복구"와 같은 맥락).
- 선택하지 않은 대안
  - Mock 상태를 파일에 저장 + 온보딩으로 복귀: 실제 서버와 같은 조건이 되고 포인트 소실을 사용자가 인지하지만, Mock 구현이 커지고 재가입 시 다시 입력해야 한다.
  - 온보딩으로 복귀, Mock은 메모리 그대로: 가장 단순하지만 앱 프로세스가 재시작될 때마다 온보딩을 다시 하게 된다.
